# voice-kit

跨项目复用的语音对话能力：**ASR → LLM → TTS**，带**输出闸门**。

从球球老师（qiuqiu.yongle.school，生产运行中）抽取。不是从零设计的框架，
是把一套已经在真实儿童用户身上跑了几个月、踩过坑改过的实现固化下来。

---

## 为什么不直接用 Pipecat / LiveKit

调研过（2026-09）。结论是**它们解决的不是我们最难的那个问题**：

| | Pipecat | LiveKit Agents | voice-kit |
|---|---|---|---|
| 供应商可插拔 | ✅ 强项 | ✅ | ✅ |
| WebRTC / 多方 / 视频 | 靠 transport | ✅ 强项 | ❌ 不做 |
| 国内供应商（MiMo/腾讯/火山） | 要自己写 adapter | 同左 | ✅ 原生 |
| **输出闸门（说出口前拦截）** | ❌ | ❌ | ✅ **核心** |

前两者假设"模型输出可信"，做儿童产品不能这么假设。而国内供应商在它们的生态里
本来就要自己写 adapter——那引入框架的成本反而高于收益。

**结论：接口按 Pipecat 的心智设计（provider 可插拔 + pipeline 可组装），实现用自己的。**
将来真要迁移不难，现在不用重写客户端编排。

## 三块

```
voice_kit/
  providers/          # 能力抽象：ASR / StreamingASR / TTS 各自独立可换
    base.py           # 接口 + ASRResult（自带 realtime_factor）
    mimo.py           # 小米 MiMo（ASR+TTS 同网关），生产验证过
    tencent.py        # 腾讯云：实时流式 ASR（WebSocket）+ 一句话识别 + TTS
  gate.py             # 输出闸门 + 输入闸门  ← 别人没有的那块
  credibility.py      # 可信度分层 + 诱导识别  ← 做儿童产品必须有
```

（客户端编排 `web/` —— VAD / ASR 抢跑 / 句级流式 / 可打断，待从球球老师抽取）

### 1. Provider：按能力分，不按厂商分

`StreamingASRProvider` 单独拎出来，因为它不是"更好的 ASR"，是**另一种架构**：

- 一次性识别耗时 ≈ 音频时长 × 0.55~0.59（**生产实测，线性**）
- 流式识别耗时与说话时长无关

调用方必须能**问得出来**谁支持谁不支持，所以有显式的 `supports_streaming`，
不要让人靠 try/except 猜。

### 2. 输出闸门：事前拦截，不是事后道歉

三层，全部从球球老师生产形态抽取：

```
① 安全垫 holdback   末尾 N 字先压住 —— 防违禁词吐一半（"抑"已显示，"郁"还在路上）
② 逐段闸门          只有检查通过的部分才下发 —— 违规内容根本不进输出流
③ 收尾全量检测       命中就整段重写，发 correction 让前端替换
```

**为什么必须事前**：说出去了就是说出去了。"我们记录了这次违规"不是答案。

这也正是**端到端语音大模型（Speech2Speech）目前不能用在儿童产品上的原因**——
音频和文字同时生成，等你看到文字，声音已经在播了。

闸门本身**不含任何具体规则**，规则由调用方注入。voice-kit 只负责机制。

### 3. 可信度分层：不判断真假，只决定采信到哪一层

起因是一次真实事件：一个叛逆期的孩子把话题引向摩托车。**叛逆期的孩子会故意对
AI 使坏**——试探边界、编故事、诱导 AI 说不该说的话。这是正常行为，产品必须假设它会发生。

两个必须分开的问题：

| | 可检测吗 | 对策 |
|---|---|---|
| **诱导**（想让 AI 说不该说的） | ✅ 有句式特征 | 识别 + 不顺着走 |
| **编造**（吹牛/说谎） | ❌ **根本做不到** | 不判断真假，改为分层采信 |

第二条是这个模块真正的设计主张。**做错的方式是加一个"说谎检测器"**——那只会产生
一个自信的错误分类器。把说真话的孩子标成撒谎，是这类产品能犯的最严重错误之一。
（`test_credibility.py` 里有一条测试专门把这个决定钉死，防止以后有人"顺手加个 is_lying"。）

正确的方式是分层：

```
自述一次        → unverified    可以聊，不写进报告结论
跨会话重复出现  → corroborated  可以进报告          ← 同一次对话说三遍不算
家长/老师确认   → trusted       可当事实
高风险主题      → needs_review  无论真假都要人看
```

**最后一条是关键。** 摩托车这个例子：如果是真的 → 安全信号，家长必须知道；
如果是编的 → 行为信号，也值得关注。**两种都需要人判断，都不该被 AI 静默写进报告
当成既定事实。** 所以不需要判断真假，只需要认出"这条不该自动通过"。

### 4. 输入闸门：命中后接管，不是过滤

球球老师的做法：红线命中时**根本不调 LLM**，直接返回写死的软回应。
模型在最危险的时刻没有发挥空间——这比"让模型小心点"强得多。

### 5. Pipeline：一套代码，多个产品

`VoicePipeline` 把三段串起来，产品差异**全部落在 `VoiceConfig` 里**——
换产品只换 config，不改一行编排代码。

| 产品 | 输出闸门 | 模型 |
|---|---|---|
| 球球老师（儿童） | 严格（8 铁律）+ 可信度分层 | `mimo-v2.5-pro`（安全回归已验证） |
| qiuyiwu.com agent | 无 | `deepseek-v4-flash`（最快） |
| AI 教练 | 中等，自定义规则 | 按场景选 |

闸门放在 pipeline 而不是 provider 里，是因为它是**产品策略**不是**供应商能力**：
同一个模型在儿童产品和成人产品里该有完全不同的输出约束。塞进 provider
会导致每换一家供应商就要重写一遍规则。测试里有一条直接钉住这个承诺——
同一句「这里有风险，我们今天就聊到这里」，儿童配置拦下、成人配置放行。

⚠️ **一个真踩过的坑**：同时做 ASR 和 TTS 的 provider（腾讯就是）上，
`stream` 是**流式 ASR**，`stream_tts` 才是 TTS。按 `stream` 优先做鸭子类型
会抓到 ASR 那个方法。`speak()` 因此**必须**先找 `stream_tts`。

## 用法

```python
from voice_kit.providers.mimo import MimoProvider
from voice_kit.gate import OutputGate, Rule

p = MimoProvider(api_url=..., api_key=...)

# TTS 流式：首块才是体感延迟
for chunk in p.stream("你好", fmt="pcm16"):
    play(chunk)

# ASR：结果自带倍速比，直接能回答"该不该上流式"
r = p.transcribe(wav, "wav")
print(r.text, r.realtime_factor)      # 0.559

# 输出闸门
gate = OutputGate(
    rules=[Rule(name="禁止主动结束对话", words=["下次再聊"])],
    rewriter=lambda text, v: call_llm_to_rewrite(text, v),
    fallback="我们再多聊一会儿吧。",
)
for ev in gate.filter(model_tokens(), low_latency=True):
    ...   # ev["kind"]: "delta" | "correction"
```

## 生产实测数据（2026-09，服务器在腾讯云）

用来判断"优化哪一段"，别凭感觉：

| | 数值 |
|---|---|
| ASR（MiMo，一次性） | **音频时长 × 0.559** — 线性，说 10 秒等 6 秒 |
| TTS 首块 | **674ms** |
| TTS 整句 | 1063ms |
| MiMo 网关 TLS 首字节 | 106~119ms |
| 腾讯 ASR 云API（非流式） | 4609ms vs MiMo 4721ms —— **基本一样** |
| 🔥 **腾讯实时流式 ASR** | **说完之后 89ms** —— 与说话长度无关 |

**两个已被证伪的假设**（省得别人再走一遍）：

1. ❌「腾讯同云所以更快」——腾讯**流式**端点 155ms 比 MiMo 119ms 还慢。
   只有非流式的云API 域名是 19ms（同地域），但那条路径不解决问题。
2. ❌「换供应商能提速」——腾讯一句话识别 4609ms vs MiMo 4721ms，差 2%。

✅ **真正的杠杆是「流式」这个架构本身，不是换谁。**
MiMo 的 `stream=true` 是**文字流式输出**（音频仍要整段传完），实测首字节
4679ms 反而比非流式全程 4246ms 更慢——对延迟零收益。

### 流式 ASR 实测（2026-09，14.9 秒音频，按 200ms/帧实时喂）

```
[基线] MiMo 一次性      14211ms      倍速比 0.955
[流式] 腾讯实时
       首个中间结果     + 645ms
       说完之后还要等      89ms      ← 用户真正感知的 ASR 延迟
省 14122ms（99%）
```

对比是公平的：真实场景里一次性是「说完 → 上传 → 识别 → 才进 LLM」，
流式是「边说边认 → 说完 89ms 就有结果」。

### LLM 首字实测（同一台服务器、同一个 prompt）

流式 ASR 上了之后，**最大的一段变成了 LLM 首字**。

| 路径 | 首字 | 换模型？ |
|---|---|---|
| `mimo-v2.5-pro` 直连 MiMo | 4337ms | — |
| `mimo-v2.5-pro` 走腾讯 TokenHub | **3282ms（−24%）** | ❌ 同一个模型 |
| `deepseek-v4-flash` 走 TokenHub | **2392ms（−45%）** | ✅ 要重验安全 |

中间那行是这个 provider 存在的理由：**换网关 ≠ 换模型**。同一个模型换条路
白拿 24%，而且因为模型行为不变，儿童产品那套 8 铁律安全回归**不用重跑**。
把「换网关」和「换模型」分成两步，风险和收益就解耦了。

⚠️ 选型的坑：`hy4-preview` / `glm-5.3-flash` / `kimi-k2.6` / `hy3` 在
max_tokens=150 时**正文一个字都吐不出来**——thinking 把配额全吃光了。
榜单分数不告诉你「孩子要等多久才听见声音」，选型必须自己量首字。

**比省时更重要的是稳定**：一次性的倍速比在 0.56~0.955 之间大幅波动
（音频越长、负载越高越慢），而流式的尾包延迟**与说话长度无关**，恒定 ~89ms。
孩子说得越多，两者差距越大——而深度用户恰恰是说得最多的那批。

### TRTC 对话式 AI：已经验过的两件事（2026-09-05，SdkAppId 1600160922）

被"要不要先买套餐"卡住是最常见的假动作，所以先用两个探针把它证伪：

```
DescribeAIConversation(假TaskId) → InvalidParameter.TaskId
    不是 AuthFailure、不是"未开通" → 鉴权和服务开通两关都过了

StartAIConversation → ✅ TaskId=v2_20260905_qrRfw7ov...  → StopAIConversation ✅
    不需要预先买 AI 智能语音套餐（475元/月）就能起任务，按量即可验证
    且它接受了 LLMConfig.APIUrl 指向我们自己的端点
```

**这就是 `openai_server.py` 存在的理由**：TRTC 把 LLM 这一段留给你自己接，
于是「用他们的编排」和「守住 8 铁律」不再是二选一。

还没验的是端到端延迟——需要一个公网可达的端点 + 一个真人对着麦克风说话。
注意官方宣传的「1s」里**不含**我们这条 LLM 的 2392~4337ms，叠起来多少只能实测。
